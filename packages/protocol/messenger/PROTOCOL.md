# bantou protocol

bantou-server is the listener of this protocol. A center (or any peer) sends a command to the server and the server replies to the sender. All messages are one JSON object in the message text. The schemas are in `protocol.json`.

## Discovery and meta

- Find servers with `list_peers` and `protocol: "bantou"`.
- Send every message with `meta: {protocol: "bantou", version: "<protocol version>"}`. The server replies with the same meta.
- `version` is the registered protocol version (this file's `protocol.json`), not the body field `bantou`. The body always carries `"bantou": 1`.

## Commands (peer to server)

- `kick_cap`: `{"bantou":1,"type":"kick_cap","cap_id":"<id>","prompt":"...","repo"?,"branch"?,"reason"?,"model"?,"worker_model"?}`. Starts the remote cap `cap_id` headlessly, or resumes it when it already has a session. `cap_id` matches `^[A-Za-z0-9_-]+$`. `repo` and `branch` must not start with `-`. `model` (claude `--model` for the cap itself) and `worker_model` (default `--model` of the workers this cap starts, remembered by the server as the cap's default) match `^[A-Za-z0-9._\[\]][A-Za-z0-9._\[\]-]*$`; both optional, absent = no `--model`. Servers older than 1.4.0 ignore them. Reply: `cap_result` when the run finishes (it can take minutes), `error` on failure.
- `stop_cap`: `{"bantou":1,"type":"stop_cap","cap_id":"<id>"}`. Closes the remote cap `cap_id`: stops its running `claude -p` (whole process group; waits until it has ended) and discards its conversation (`state.json` `session_id` -> null; idle / failed / running all accepted), so the next task starts a new session. `logs/` and worker dirs are kept. Reply: `stop_result` (`stopped` is false when the cap was not running), `error` on failure. The interrupted `kick_cap` still gets its own `cap_result` with `ok:false`.
- `status`: `{"bantou":1,"type":"status","cap_id"?}`. Reply: `status_result` (carries the server identity from 1.7.0, see below). `cap_id` (1.6.0): the server also takes the sender as the center to notify for that cap. A server older than 1.6.0 ignores it.
- `hello`: `{"bantou":1,"type":"hello"}`. Asks the server for its npm version and update state. Reply: `hello_result`. Servers older than protocol 1.3.0 do not know it and do not reply.
- `update_server`: `{"bantou":1,"type":"update_server","version":"<semver>"}`. Tells the server to update itself to npm `bantou@<version>` and restart once every running cap and worker is done (the package source is the server's own config, never this message). Reply: `update_result` (`waiting` right away; it does not wait for the runs), `error` on failure. While it waits, `kick_cap` and `task` are refused with `error` `code:"updating"`, `retryable:true`. `stop_cap`, `status`, `hello` are still served.
- `task` (1.5.0): `{"bantou":1,"type":"task","cap_id","task_id","goal","repo"?,"branch"?,"deliverables":{"branch"?,"report_path"?,"other"?},"verify":{"tests"?,"steps"?},"constraints":[...],"workers":{"items"?:[{"id"?,"role","scope","model"?,"depends_on"?}]},"worker_model"?}`. Gives the remote cap `cap_id` a task; the server builds the cap's first instruction from the fields (the same cap_id again resumes the cap). `role` is `implement` | `review` | `docs` | `test` | `other`. No `workers.items` = the default of at least 2 workers (one implement, one review). Reply: `task_result` when the run finishes, `error` on failure. A peer older than 1.5.0 does not know it.
- `worker_reply` (1.5.0): `{"bantou":1,"type":"worker_reply","cap_id","worker_id","text"}`. The server runs `worker_start` with the same `worker_id` and `text` as the prompt. Reply: `worker_reply_result`, `error` on failure (unknown cap, a worker of another cap).
- `retire_server` (1.8.0): `{"bantou":1,"type":"retire_server","server_id"?,"reason"?}`. Retires the server for good: it refuses new `kick_cap` / `task` / `worker_reply` / `worker_start`, stops every running cap and worker, unregisters from the messenger, releases the host lock, and exits together with its supervisor and launcher (exit code 76, which `RestartPreventExitStatus` keeps systemd from restarting). It writes `<workspace>/server.retired` first; the server then refuses to start until that file is removed. `server_id` (optional): when given and different from the server's own, the server answers `error` and stops nothing. A center should send it: all servers are named `bantou-server`. Reply: `retire_result`, or `error`. A control command like `update_server`: accepted whatever the sender's protocol version is. **A server older than 1.8.0 ignores it and sends no reply; a center sends it only to a server whose declared protocol version is 1.8.0 or later (`supportsRetire`), and never reads "no reply" as "retired".**
- The shape of `hello`, `hello_result`, `update_server` and `update_result` is fixed for good, and a center sends them to servers of any protocol version (1.3.0 and later). They are the only way to update a server whose protocol version differs from the center's.

## Replies (server to peer)

- `cap_result`: `{"bantou":1,"type":"cap_result","cap_id","session_id","ok","result_text","error"?}`. Also sent later, to the center that kicked the cap, when a worker report resumes the cap.
- `stop_result`: `{"bantou":1,"type":"stop_result","ok":true,"cap_id","stopped","session_cleared"?,"previous_session_id"?}`. `session_cleared` / `previous_session_id` are optional and additive (no version bump): absent = the server only stops and did not discard the conversation. `status_result` caps / workers may carry an optional `conversation` (`started_at`, `tasks`, `context_tokens`, `context_window`, `context_percent`, `usage_at`, `last_error_text`?).
- `status_result`: `{"bantou":1,"type":"status_result","ok":true,"caps":[...],"workers":[...],"server_id"?,"host"?,"user"?,"workspace"?,"server_version"?,"protocol_version"?}`. The optional fields are the server identity (1.7.0, below).
- `hello_result`: `{"bantou":1,"type":"hello_result","ok":true,"server_version","protocol_version","server_id"?,"host"?,"user"?,"workspace"?,"update":null|{"state":"waiting"|"restarting","from","to","running":{"caps","workers","reports"}},"last_update":null|{"to","ok":false,"error","at"}}`.
- Server identity (1.7.0, in `hello_result` and `status_result`, all optional): `server_id` (stable per workspace, `^[A-Za-z0-9_-]{1,64}$`, kept in `<workspace>/server.json`; survives restart and self-update), `host` (`os.hostname()`), `user` (OS user of the server), `workspace` (absolute path). `server_version` is the npm `bantou` version; `protocol_version` is the registered protocol version. A server older than 1.7.0 sends none of them: a center identifies such a server by its messenger peer id.
- `update_result`: `{"bantou":1,"type":"update_result","ok":true,"state":"current"|"waiting"|"restarting","from","to","running":{"caps","workers","reports"}}`.
- `task_result` (1.5.0): `{"bantou":1,"type":"task_result","cap_id","task_id","state":"done"|"failed","summary","workers":[{"worker_id","role","state","branch"?,"commit"?,"tests"?,"report_path"?,"result"}],"review":{"verdict":"ok"|"issues"|"unknown","items":[{"severity":"high"|"medium"|"low","text","resolved"}],"rounds"},"remaining":[...],"error"?}`. Taken from the cap's final answer; when no JSON can be read, `summary` is the raw answer, `workers` and `remaining` are empty and `review.verdict` is `unknown`. Also sent, to the center that sent the `task`, when a worker report resumes the cap and the cap answers with the JSON.
- `worker_reply_result` (1.5.0): `{"bantou":1,"type":"worker_reply_result","ok":true,"cap_id","worker_id","accepted":true}`.
- `retire_result` (1.8.0): `{"bantou":1,"type":"retire_result","ok":true,"state":"retiring","stopped":{"caps","workers"},"exit_at","exit_code":76,"host_steps":[...],"service"?:{"manager":"systemd"|"launchd"|"none","name"?,"detected"?},"server_id"?,"host"?,"user"?,"workspace"?}`. Sent before the server goes away; the server exits after `exit_at` (a few seconds later), so the next thing a center sees is the peer disappearing. A second `retire_server` in that time gets the same reply. `host_steps` (1 to 3 shell lines, values shell-quoted) is what an operator with root does on the host: remove the service unit, the OS user, the workspace. The server cannot do it: it runs as an unprivileged user. `service.detected` false means the name is the `install-service.sh` default, not confirmed from the process.
- `error`: `{"bantou":1,"type":"error","ok":false,"message","command"?,"cap_id"?,"worker_id"?,"task_id"?,"code"?,"retryable"?,"retiring"?}`. `retiring:true` (1.8.0): the server accepted `retire_server` and refuses this command for good (`retryable` is false). An older center ignores the field. `code`: `updating` | `update_failed` | `update_conflict` | `invalid_version` | `version_mismatch`. `retryable:true` means the same command may be sent again later.

## Notices (server to peer)

- `activity`: `{"bantou":1,"type":"activity","cap_id","at","agents":[...]}`. Not a reply: it is never matched with a pending command. Sent to the center that kicked `cap_id`, as a snapshot of the cap and its workers (cap first, then workers by id). Each agent has `kind`, `id`, `cap_id`, `state` (running | stalled | idle | done | failed | lost), `task`, `last_activity`, `last_output_at`, `silent_ms`, `started_at`, `finished_at`, `error`?, `model`? (string or null; absent from servers older than 1.4.0). Sent every 5 seconds while any agent is running or stalled, and at each state change. Use `silent_ms` for elapsed time, not clock differences. A peer that does not know `activity` ignores it.

- `worker_report` (1.5.0): `{"bantou":1,"type":"worker_report","cap_id","task_id"?,"worker_id","kind":"progress"|"ask"|"approve"|"done","text","at"}`. Not a reply. Sent to the center that kicked `cap_id` for every report of a worker, in parallel with the resume of the cap. `task_id` is the latest `task` of the cap (absent when the cap has had none). A peer that does not know `worker_report` ignores it.

## Notes

- The server ignores messages that are not commands. Messages without `meta` are still accepted as the old format.
- The peer id changes when a peer re-registers; replies go to the sender's current peer id.
- Notices (`activity`, `worker_report`) and the replies that follow a worker report go to the center of the cap. The server remembers that center by its peer **name** and resolves it to the current peer id when it sends (1.6.0); every command with a `cap_id` (`kick_cap`, `task`, `worker_reply`, `stop_cap`, `status` with `cap_id`) updates it.
- Changing this definition requires a new `version` (same name and version with different content is a PROTOCOL_CONFLICT).
